## 1. 阶段目标

完成后，现有 Demo 必须先达到“导航稳定、解析不误写、表单可操作、业务事实正确、通知可追溯”的状态：

- 从任何入口切换账号、冷启动或刷新都落到对应首页，不恢复旧页面或自动弹草稿；
- 关闭“该吃药啦”回长辈首页，不写事实、不消耗延后；
- 助手理解否定/改口，并能修改当前计划草稿；
- 加药页在窄屏不再向右挤压；
- “未服用”只在原自然时段截止后且无延后保护时允许本人记录；
- N2 提前轮和截止轮按同一双端接收范围分别发送、分别去重；
- v2 存档可安全迁移到结构版本 3，旧历史不被改写。

本阶段不是视觉改版阶段。首页卡片顺序、主按钮造型、完整五组时段分块、子女日历和话筒图标留给第二阶段。

## 4. P0-01：账号切换、冷启动与草稿落点

| 项目 | 实施要求 |
| --- | --- |
| 主要文件 | `app.js`；必要时 `demo.js`、`demo-bridge.js`；浏览器测试 |
| 代码锚点 | `view` 初始化、`rememberView()`、`sessionKey()`、`preserveDraft()`、`resumeDraft()`、`switchAccount()`、`switchProfile()`、`closeModal()`、`render()` |
| 当前根因 | `switchAccount()` 合并 `sessionViews` 的旧 `page/modal`，随后直接 `resumeDraft()`，导致恢复旧页面并自动打开旧弹窗 |
| 目标状态 | 长辈：`page='home'`、`planTab='active'`、`historyDate=today()`、`selectedProfileId` 归一到本人；子女：`page='home'`、保留合法 `selectedProfileId`；两端都不恢复旧 modal，符合资格的新聚焦提醒只能在首页建立后按规则出现 |

### 4.1 改什么

1. 建立唯一的“进入账号首页”状态重置函数，供首页账号入口、“我的”入口和 demo bridge 共用。
2. 切换前调用现有草稿保存，但切换后不再合并旧页面、滚动位置或 modal。
3. 保留以 `accountId|profileId` 隔离的草稿内容；目标账号只显示“继续未完成的输入”，用户点击后才调用 `resumeDraft()`。
4. 清除来源账号的 `modal`、`modalReturnFocus`、`undo`、`overdueOpen`、聚焦队列和仅对原页面有效的临时路由状态，不把这些状态带给目标账号。
5. 目标首页完成后，可按最新任务资格重建该账号的聚焦候选；这不是恢复草稿。目标账号本轮已经关闭的任务不能因往返切换被清空后立即重弹。
6. 冷启动与整页刷新只从 sessionStorage 恢复合法账号、档案和显示设置；页面强制回目标首页，不恢复旧 modal。
7. 主题切换、同一实例返回桌面不属于冷启动，继续保留当前页面与草稿。
8. 有效通知深链只能在重新核验账号和档案权限后定位；无效/撤权链接回首页并给出反馈。

### 4.2 不能做

- 不删除或跨账号合并草稿；
- 不清空业务 `localStorage`；
- 不把 `switchProfile()` 的正常档案切换误改成账号切换；
- 不通过增加延时或重复 `render()` 掩盖状态问题。

### 4.3 自动与浏览器验证

- 新增账号切换状态的可测试纯辅助函数，或用浏览器断言验证完整状态；
- 分别从首页右上角、“我的”现有入口、`demo.html` 连续往返切换至少 5 次；
- 在两个账号分别留下聊天和身体数据草稿，确认只出现继续入口，点击后恢复正确对象；
- 子女先选择另一位长辈，再切到长辈账号，确认档案强制归一到该账号本人；
- 在 `plans/history`、`health`、聊天 modal、健康 modal 等状态下切换，目标端始终回首页；
- 刷新两端验证首页落点；再验证主题切换和返回桌面仍保留实例内页面；
- 内部门槛 `S1-A01` 覆盖首页右上角、“我的”现有入口和 demo 舞台的同一切换语义；执行 `V3-A02`、`V3-A40`。它只为 `V3-A01` 提供功能证据，后置的“我的”左上新入口完成前不得把 `V3-A01` 整项标为通过。

通过条件：所有入口行为一致，测试中不存在自动弹出旧 modal、草稿串对象或页面闪回。

## 5. P0-02：关闭“该吃药啦”回首页

| 项目 | 实施要求 |
| --- | --- |
| 主要文件 | `app.js`、浏览器测试 |
| 代码锚点 | `locateTask()`、`dismissFocus()`、`advanceFocus()`、`scheduleFocus()`、聚焦 modal 渲染 |
| 当前根因 | `dismissFocus()` 关闭后调用 `locateTask()`，该函数固定把页面改到 `plans/history` |

### 5.1 改什么

1. 关闭聚焦提醒时标记本次访问内已关闭的队列，清除 modal，然后进入长辈 `home`。
2. 关闭动作不得调用 `locateTask()`；保留一个明确命名的“查看对应任务”按钮，只有点击它才定位任务。
3. 关闭不写入声明、不改变任务状态、不消耗延后次数、不触发第二次即时弹窗。
4. 多任务聚焦队列中，“完成当前任务”可以按既有规则进入下一项；单纯关闭整个提醒则回首页并结束本次队列展示。
5. 保留关闭按钮的可访问名称、焦点处理和 `inert` 清理。

### 5.2 验证

- 从长辈首页自动聚焦、N1 通知和账号切换后聚焦三种来源分别关闭；
- 对比关闭前后任务 `status`、`changes`、`snoozeUsed`、通知日志，必须无事实变更；
- 点击“查看对应任务”才允许定位，浏览器后退/关闭后仍可回首页；
- 对应验收：`V3-A03`、`V3-A07`。

通过条件：关闭与查看成为两个独立动作，任何关闭路径都不再落到打卡记录页。

## 6. P0-03：助手否定与改口解析

| 项目 | 实施要求 |
| --- | --- |
| 主要文件 | `conversation.js`、`tests/conversation.test.cjs` |
| 代码锚点 | `intent()`、`parsePlan()`、剂量正则、餐时否定/替换规则 |
| 当前根因 | `parsePlan()` 取最后一个剂量匹配，“不是 2 片”中的 2 会覆盖前面的肯定值 |

### 6.1 改什么

1. 先切分肯定、否定、改口连接词及其作用范围，再选择最终候选，不能只用“最后匹配胜出”。
2. 支持并测试：
   - “每次 1 片，不是 2 片” → 1 片；
   - “不是一片，是半片” → 0.5 片；
   - “一片改成半片” → 0.5 片；
   - “饭前改饭后” → 餐后；
   - “不是饭后”且没有新值 → 保留原草稿并追问；
   - 多个互相冲突的最终值 → 阻止核对。
3. 解析返回继续区分“已确定字段”“候选冲突”“必须澄清”，原始文字不得丢失。
4. 不扩大到自由文本大模型，不通过药名猜剂量，不把“还没吃”直接记录成未服用。

### 6.2 验证

- 在 `tests/conversation.test.cjs` 增加肯定值后跟否定值、否定后改口、半片、小数和餐时用例；
- 浏览器从加药助手输入同样句子，检查聊天摘要、配置卡和核对页；
- 无法可靠解析时保存按钮保持阻止状态；
- 对应验收：`V3-A34`。

通过条件：所有入口得到同一最终值，被否定内容不会进入核对或存档。

## 8. P0-09：结构版本 3 与迁移骨架

该任务必须先于 N2 规则落地，避免先写通知再补字段。

| 对象 | 第一阶段字段与迁移要求 |
| --- | --- |
| 时段设置 | 保留兼容读取旧 `time`；v3 明确 `reminderTime`、`missedAlertTime`，分别代表 N1 和 N2 提前轮 |
| 当次任务 | 快照/字段可追溯到 `reminderTime`、`missedAlertTime` 和原自然截止 `deadlineAt` |
| N2 日志 | 增加 `warningRound=early|deadline`、`receiverId`、`notificationId`、`sentAt`/发送状态；唯一语义为任务+接收人+轮次 |
| 默认数据 | `seed-data.js` 升级为 version 3；四时段 N1 默认 `08:00/12:30/17:30/21:00`，N2 提前默认 `09:00/14:00/19:00/22:00` |
| 校验 | `validData()` 对本阶段新增字段、轮次、时间范围、引用关系和通知状态做严格校验；迁移计划/旧任务的 `missedAlertTime=null` 是唯一允许的待确认表示 |

本阶段的 version 3 只落核心导航/时段/N2 字段。后置 P1-08 的 mg 字段不得提前物化；未来 P1-08 必须让已存在的 version 3 计划在缺少可选 mg 字段时仍可幂等补齐，同时继续保留 `doseValue/doseUnit` 和旧任务快照。

### 8.1 迁移顺序

1. 复制原数据，不在原对象上试探性改写。
2. v2 `slotSettings.time` 迁移为 N1 `reminderTime`。
3. 旧计划只有在默认 N2 提前时间晚于自定义 N1 且仍处于同一自然时段时才安全补入；否则写成 `missedAlertTime=null`，表示提前轮未启用、待用户在第二阶段明确确认，不能静默造值。新计划必须保存有效 N2 默认值。
4. 截止轮始终来自任务原 `deadlineAt`，不创建可编辑截止时间。
5. 能可靠关联任务和接收人的旧 N2 截止通知标为 `warningRound=deadline`；信息不足时保留 legacy，不伪造接收人或发送状态。
6. 已完成/已取消的历史任务继续使用旧快照，缺少提前时刻时保持 null 且不参与新 N2；仍待处理的旧任务保留原 `deadlineAt`，只在其计划可安全迁移时获得同业务日 `missedAlertTime`。父计划迁移不得改写历史药名、剂量、餐时、提醒或截止时间。
7. 无效存档保留原文并进入临时演示降级，不得在后续操作时覆盖原存档。
8. 本阶段恢复初始数据生成“当前阶段完整”的 version 3 核心结构，并清除草稿、N2 两轮发送记录和临时交互状态；不得声称已经生成后置 mg、血糖、重新启用或模拟身份结构。

后置 P1-08、P2-01、P2-02 或 P2-03 启动时，不能只看 `version===3` 就跳过自己的字段归一化；应检测各自的 mg 字段、血糖提醒配置、重新启用关联或模拟身份状态是否实际存在，再对已有 version 3 存档做幂等补齐。阶段一不得提前创建这些后置数据。

### 8.2 测试

- 新增固定的最小 v1 与 v2 fixture；不得继续把会升级到 version 3 的 `SILVER_SEED_DATA` 临时改写成“旧版 fixture”；
- 显式验证 `v1 → v3 核心结构`、`v2 → v3 核心结构` 以及迁移结果再次加载的幂等性，旧枚举、来源和历史事实均不得被静默重解释；
- 新增 v2 正常存档、缺字段、旧 N2 日志、跨时段非法默认值、无效 JSON 和引用损坏用例；
- 验证迁移幂等：同一 v2 输入重复迁移结果一致；v3 再读取不重复追加字段或日志；
- 验证 `localStorage` 键名保持不变；
- 本阶段使用内部迁移门槛 `S1-M01` 覆盖时段、N2 日志和旧任务快照，并执行 `V3-A37`、`V3-A39`。这些结果只为 `V3-A36` 提供核心迁移证据；由于 mg 和血糖子结构后置，不得在本阶段把 `V3-A36` 的全量第 12 章迁移标为通过。

通过条件：结构版本 3 的核心子集可保存、重载和恢复当前阶段默认数据，旧历史和无效原存档均不被误写；未宣称后置模块的全量 v3 恢复已完成。

## 9. P0-06：“未服用”的统一业务资格

| 项目 | 实施要求 |
| --- | --- |
| 主要文件 | `rules.js`、`app.js`、`conversation.js`、规则/助手/浏览器测试 |
| 代码锚点 | `stateOf()`、`canDeclare()`、`recordDose()`、`doseActions()`、助手声明分支、历史更正入口 |

### 9.1 建立单一规则函数

新增或重构一个纯规则入口，统一回答“当前能否新记录为未服用”及拒绝原因。必须同时满足：

1. 操作者是任务所属长辈本人；
2. 当前完整时刻达到原 `deadlineAt`；
3. 任务未取消、未失效；
4. 当前不在有效延后保护期；
5. 对新增声明，任务尚未有最终事实。

首页、逾期卡、任务详情、确认弹窗和助手必须调用同一规则，不能只隐藏按钮。历史更正单独依据“原截止已过 + 本人权限 + 可更正事实”判断，不能因为任务已 resolved 而拒绝。

### 9.2 验证矩阵

| 场景 | 预期 |
| --- | --- |
| 截止前说“没吃” | 保持待打卡，说明尚未到截止，不写记录 |
| 截止后无保护 | 本人可选择未服用 |
| 截止后仍在延后保护 | 暂不可记录未服用 |
| 已记录历史在截止后更正 | 本人可更正，保留前后版本 |
| 子女手动/助手尝试 | 始终拒绝，不改变数据 |
| 取消或失效任务 | 拒绝并给出原因 |

对应验收：`V3-A08～A10`。通过条件：所有入口的允许/拒绝结果和文案一致，系统从不自动写入未服用。

| 通知 | 触发 | 接收人 | 页面状态 | 事实影响 |
| --- | --- | --- | --- | --- |
| N2 提前轮 | `missedAlertTime` 到达且任务仍未记录 | 任务所属长辈 + 每位当前已授权子女 | 仍为待打卡 | 无 |
| N2 截止轮 | 原 `deadlineAt` 到达且任务仍未记录 | 使用与提前轮相同的资格公式，按截止轮发送时的实时授权重新计算 | 显示未按时打卡 | 不自动记录未服用 |

### 10.1 改什么

1. 拆分 `notificationEligible()` 和 `notificationRound()` 对 N2 的单轮假设，显式计算 `early` 与 `deadline`。
2. `evaluateNotifications()` 对每个任务、每位当前接收人和每个到期轮次分别评估。
3. “两轮接收人相同”指资格公式都为任务所属长辈加当前已授权子女，不是冻结提前轮名单；每轮发送时重新读取授权关系。
4. 提前轮已发送不占用截止轮资格；截止轮也不能反向补写提前轮。
5. 两轮正文都只表达“尚未收到打卡”，截止轮可以说明已到自然时段结束，但不能断言未服药。
6. 页面“未按时打卡”仍由 `stateOf()` 基于自然截止判断，不由通知是否送达决定。
7. 渲染函数不得产生通知；仍由 `commit()` 调用统一协调器，演示时钟变化按现有受控路径触发协调。
8. 防御性拒绝 N2 早于/等于 N1、跨出自然时段或字段无效的计划，不在运行时猜测或跨时段补发。

### 10.2 测试

- 早餐 09:00：长辈与全部授权子女各收到一次提前轮，任务仍 pending；
- 早餐 11:00：按当时授权重新计算的接收人各收到一次截止轮，任务 overdue，无 not_taken 事实；
- 提前轮发送后在截止前完成任务：不再发截止轮；
- 两名授权子女分别有独立幂等记录；
- 提前轮后撤销子女 A 并新授权子女 B：截止轮只发长辈和 B，A 的历史提前轮记录仍保留；
- 睡前任务跨业务日期到 `00:00` 的截止轮仍关联原任务日期，不重复或漏发；
- 重复 render 不产生通知；
- 对应验收：`V3-A16`、`V3-A17`、`V3-A43`。

通过条件：同一持续未记录任务形成两轮、同接收范围、互不覆盖的通知记录，页面状态和事实状态正确。

## 11. P0-08：延后保护、权限、幂等与重试

### 11.1 完整时刻分支

| 保护结束时刻 | 应做什么 |
| --- | --- |
| 早于 `missedAlertTime` | 继续等待原提前触发时刻 |
| 已到提前时刻但早于 `deadlineAt` | 只发送仍有时效的提前轮 |
| 已到或超过 `deadlineAt` | 只发送截止轮，不补发过时提前轮 |

保护期内不发送两轮 N2、不显示未按时红点、不允许 N3 家属主动提醒。延后仍只有一次机会，5/30 分钟二选一，不改变原自然截止或服药事实。

### 11.2 幂等与停止条件

1. 唯一键必须覆盖 `taskId + receiverId + warningRound`，不能只按任务或通知种类去重。
2. 离线/失败重试复用原通知 ID；重试前重新检查任务状态和接收权限。
3. 任务完成、取消或失效后，两轮均停止。
4. 某子女撤权后只抑制该接收人，长辈和其他授权子女不受影响。
5. 失去资格的待发送通知标记为 suppressed 或等价可追溯状态，不在恢复在线时补发。
6. N3 继续使用既有共享冷却，不能与 N2 轮次共用幂等键。

### 11.3 测试

- 保护跨过提前时刻但未跨截止；
- 保护同时跨过提前和截止；
- 完成/取消/失效/撤权发生在排队后、重试前；
- 提前轮离线排队后跨过截止再上线：旧提前轮转为 suppressed，只发送/保留截止轮，不补发过时提前轮；
- online/offline/failure 三模式及原通知 ID 复用；
- 重复 `commit()`、刷新、协调和重播均不重复；
- 对应验收：`V3-A44`、`V3-A45`。

通过条件：每位接收人每轮最多一次，没有过时补发、撤权泄露或由通知写成服药事实。
