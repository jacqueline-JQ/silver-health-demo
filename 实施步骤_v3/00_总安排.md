## 4. 每个阶段的固定执行流程

1. **读取范围：**读取 `AGENTS.md`、MVP v3、本总安排和当前阶段文档；只按当前阶段施工。
2. **核对工作区：**确认分支、HEAD、未提交改动和已有进度；不覆盖用户或其他 Agent 的修改。
3. **建立基线：**运行 Node 规则测试、相关浏览器测试并保存结果；已有失败必须记录，不得伪装成新回归。
4. **逐任务实施：**同一时间只推进一个任务编号；每项先改规则/数据，再接 UI，再加测试。
5. **任务级验证：**针对性检查通过后，才在阶段文档中勾选该任务；失败就留在本任务处理。
6. **阶段级回归：**运行当前阶段全部新增测试和受影响的 v2 回归；检查两个账号、两个字号、三系统与关键视口。
7. **保存证据：**JSON、截图和人工检查记录写入当前阶段专属目录，不覆盖 v2 证据。
8. **更新记录：**把实际修改文件、命令、通过数、未执行项、残余风险和提交号写回阶段文档。
9. **提交与标记：**完成条件全部满足后再提交并添加阶段标签；未通过不得标记完成。
10. **阶段停止：**向用户报告后停止。进入下一阶段需要新的明确启动指示。

## 6. 测试与证据约定

### 6.1 固定命令

先确认 Playwright wrapper 所需的 `npx` 可用：

```bash
command -v npx >/dev/null 2>&1
```

Node 规则测试：

```bash
node --test tests/*.test.cjs
```

本地预览：

```bash
python3 -m http.server 8765 --bind 127.0.0.1
```

浏览器脚本：

```bash
TEST_BASE_URL=http://127.0.0.1:8765 TEST_THEME=<主题> TMPDIR=/tmp \
  node tests/browser-runner.cjs tests/<阶段脚本>.browser.js \
  output/playwright/<阶段目录>/<脚本名>-<主题>.json
```

若使用 Playwright CLI，设置短 socket 目录，避免 macOS 路径过长：

```bash
PWTEST_SOCKETS_DIR=/tmp/pwya /Users/jacqueline/.agents/skills/playwright/scripts/playwright_cli.sh -s=<会话名> open http://127.0.0.1:8765/index.html
```

第一阶段必须先让受影响的浏览器脚本统一读取 `TEST_BASE_URL`，默认仍为 `http://127.0.0.1:8765`。在该基础设施修改完成前必须使用 8765；完成后端口被占用才可换用空闲端口，并在**每一条**浏览器命令和 Playwright CLI 地址中传入/使用同一个实际地址。测试浏览器应使用独立存储，不连接用户日常浏览器。

## 7. Git 提交与版本标记

- 每阶段可有中间提交，但只有全部完成门槛通过后才能创建计划完成标签。
- 收尾采用“实现提交 → 封口提交 → 标签”的顺序：先完成代码/测试提交；再在阶段文档中记录最后实现提交和实际验证，形成封口提交；完成标签指向封口提交。文档不填写无法自引用的封口提交哈希。
- 封口提交应包含当前阶段文档的真实完成记录和必要验收索引；大体积证据按项目既有规则提交，不把本地私有存储备份纳入版本库。
- 计划完成提交信息：
  - 阶段 1：`feat: 完成MVP v3第一阶段P0`
  - 阶段 2：`feat: 完成MVP v3第二阶段核心界面`
- 计划标签：`mvp-v3-stage-01-p0`、`mvp-v3-stage-02-p1-core`。
- 不覆盖已有标签，不使用 `git reset --hard` 或 `git checkout --` 丢弃工作。
- 默认只做本地提交与标签；是否推送由阶段启动指示或用户最新指示决定。

## 8. 暂停条件

出现以下任一情况必须留在当前阶段，不得勾选完成或进入下一阶段：

- 需要改变 MVP v3 已确认规则才能继续；
- 数据迁移会覆盖、删除或伪造旧记录；
- 子女权限边界无法同时满足手动入口、助手和通知；
- N2 去重、延后保护或离线重试仍有重复/漏发但原因未明；
- 关键浏览器流程有 JavaScript 错误、不可操作控件或存储刷新后不一致；
- 当前工作区出现无法判断来源且与本阶段冲突的修改；
- 必要测试工具经合理排查仍不可用。

普通 CSS 参数、函数拆分和测试组织方式由 Agent 自行决定并记录，不因这类实现细节暂停。

## 9. 回退方式

1. 回退前先记录当前 `git status`、HEAD、失败命令和证据，保护未提交工作；首次运行真实迁移前，把兼容存储键的原始值备份到隔离、非 Git 的临时位置。
2. 优先从阶段开始提交创建临时分支或额外 worktree 比较，不直接丢弃后续提交。
3. 已提交阶段需要撤销时使用新的 `git revert` 提交；不改写远端历史。
4. 数据结构已升级时，不能尝试把已写入的 version 3 有损降回 version 2。回退代码必须保留 version 3 的只读兼容层，或在用户明确同意后只对隔离测试存储恢复迁移前快照；不能仅回退 UI 而留下无法读取的新存档。
5. 标签只在阶段完整通过时创建；失败的中间状态不复用计划完成标签。
