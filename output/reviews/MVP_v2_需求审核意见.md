# MVP v2 需求审核意见

审核对象为当前工作区的《老年人智慧健康管理_MVP文档_v2.md》（986 行）。v2.1 过渡稿已在页首声明归档，本文以 v2 主文档为实现基准；v1 和现有代码仅用于核对继承规则及实现影响。

**结论：实现前最需要收敛的是时间判定、服药事实、聚焦卡生命周期和计划生效规则。另有两类文档维护问题：已确认决议没有同步到前文；“去 PRO”章节混入了尚无完整规格的新功能。**

本文是审核意见，所有“建议”均未替用户写成已确认需求。未修改现有需求文档或代码，未把文档检查当成浏览器或实机验收。

## 1. 建议实现前处理的七项问题

### R01 · P1：延后到期与逾期判定存在两种写法

**证据：**[§6.4 保护期结束][v2-snooze-end]要求“延后时刻到达后仍未服用，且当前时间已超过原自然时段结束点”，才结算逾期；[D06][v2-d06]却写成“保护期结束后仍未记录则逾期并按 N2 发送”，漏掉原时段条件。

**触发场景：**早餐 08:10 延后 5 分钟，08:15 仍未记录。按正文，应继续待打卡，到 11:00 才逾期；按 D06，可以在 08:15 就点红并向子女发送 N2。这不是同一种实现。

另一个端点问题是：[§5.3][v2-slot-boundary]已规定左闭右开，§7.3 表格却多次写“超过 11:00/16:00”，而末段又说“11:00 逾期”。延后示例也有“16:20 处于保护期”与“延后时刻到达后立即结算”的表述差异。必须明确恰好等于截止时刻时的状态。

**建议口径：**使用以下统一业务条件，并让红点、N2、看板、历史和验收全部引用它：

```text
未按时打卡 = 没有明确记录
             且 当前时间 >= 原时段截止
             且 当前不处于有效延后保护期

有效延后保护期在 当前时间 == 延后到期时间 时结束。
```

比较时刻应包含任务业务日期与明确时区，不能只比较 HH:mm。这保留了已经确认的自然时段规则。08:15 仍在早餐时段时只再次提醒，不提前判逾期。应把 D06 的摘要补完整，而非重新引入“提醒后若干分钟逾期”的旧逻辑。

### R02 · P1：部分文案把“没有打卡”变成了“确定没有服药”

**证据：**[§5.3][v2-overdue-wording]把自动超时状态写成“逾期未服”；[§7.3][v2-states]则明确“未按时打卡”不代表未服用。多个延后段落还使用“仍未服用”作为计时器判定条件。计时器实际能判断的是有无记录。

**触发场景：**长辈实际已经吃药但忘记记录，系统到时显示“逾期未服”，或者使用“已延后过 1 次，请尽快服用”。后者在补记或旧通知场景下，可能把核对记录变成再次服药的催促。

[§7.3 的“延时服用”][v2-late]也没有覆盖完整情况：它定义为晚于提醒时间但仍在自然时段内，或在延后保护期内；早餐药实际在 11:30 才服用、且没有延后时，反而没有明确归类。实际时间不详的展示也仍依赖 D04。

**建议口径：**自动状态统一使用“待打卡 / 未按时打卡”；“未服用”只能来自本人声明。延后次数耗尽可提示“延后机会已用完，请按实际情况记录”。原始时段、晚于提醒、超出时段、补记和实际时间不详分别作为可追溯信息；不要让补记时间或通知状态直接决定服药事实。到点提醒仍可保留“该吃药啦”，补记/逾期核对场景应使用相应文案。

### R03 · P1：全屏聚焦卡缺少完整的出现、退出和连续处理规则

**证据：**[§9.3][v2-focus]规定打开首页有当前待服药物就自动呈现；[动作定义][v2-focus-actions]规定点击延后关闭，之后再次弹出。但没有明确关闭入口、多药队列、同一次访问的重复触发条件，以及正在填写表单时的处理。

**触发场景：**15:50 延后到 16:20，关闭卡片后回到首页，任务仍未记录。若控制器按“有待服药就弹”执行，会马上再次弹出；只想查看血压的人也可能被迫选择一种服药状态才能离开。另一个待定点是 05:01 打开首页、早餐提醒设在 08:00，此时是否应立即出现“该吃药啦”。

**建议本次明确以下行为：**

| 情况 | 建议行为 |
| --- | --- |
| 主动打开首页 | 明确按“进入自然时段”还是“已到提醒点”触发；推荐已到提醒点且任务未记录时自动呈现，时段内可自行进入记录 |
| 延后保护期内重返首页 | 不自动再次弹出同一任务；允许用户主动进入核对 |
| 多个任务同时到点 | 稳定排序，逐项处理，显示“第 X / Y 项”；单项动作不能批量确认其他药物 |
| 用户暂不处理 | 提供明确关闭/稍后查看入口；关闭不写服药记录、不消耗延后机会 |
| 已有表单、语音草稿或其他弹窗 | 保留当前输入，提醒排队或只显示提示；不覆盖未保存内容 |
| 已记录、取消或失去授权的旧通知 | 按 §9.5 已有要求读取最新状态，进入结果/失效说明，不重新呈现可重复打卡的动作 |
| 延后到点 | 原型及应用前台可展示应用内卡片；真实 APP 后台/锁屏先发系统通知，用户打开后再展示卡片 |

最后一项用于协调“定时再次弹出通知与卡片”和 §9.7 的真实系统通知架构，不能把前台原型的定时器视为后台唤起界面的实现。

### R04 · P1：一键“已服用”应写入什么事实，以及之后如何更正，没有闭合

**证据：**[§6.3][v2-actual-dose]要求确认实际时间、实际数量和单位，不能把计划剂量直接视为实际已服剂量；[§9.3][v2-focus-actions]的一键动作只规定成功反馈、关窗和打勾。§12.1 虽列出更正痕迹，却没有给出更正入口和状态转换。

**触发场景：**计划 2 片，长辈实际只吃了 1 片，直接点击全屏卡“已服用”；或者 09:00 点击时实际在 08:00 已服。开发者可能保存“计划 2 片、现在服用”，也可能只保存一个已服用状态，两种实现都能满足当前按钮文字，却不能产生相同事实记录。

还有“到现在还没有服用”的分支：§6.6 将它保存为“未服用”。如果长辈后来服用了，必须能将这次记录更正，而不能被一个永久完成状态锁住。[现有 recordDose][code-record]对已处理事件直接返回，照搬它无法提供这个转换。

**建议口径：**快捷按钮要明确本人在确认什么。例如可用“现在已按上述剂量服用”作为明确快捷声明，同时提供“时间/数量不同”入口；不宜不加说明地自动填入实际量和实际时间。保留 v1 [已有的 5 秒撤销][v1-undo]，并补充超过撤销期后的本人更正流程，保留旧值、修改时间和操作者。更正后同步刷新统计、通知和历史。

这不意味着所有一键操作都必须再加一层确认；关键是快捷声明的含义明确，例外有入口。

### R05 · P1：新建、编辑、停用怎样改变当天任务和日历分母，仍需定稿

**证据：**[D07][v2-d07]标题包含“新建/停用生效”，内容却只解释补记。§7.2 和 §12.1 要求保留计划版本、历史快照与任务有效性，但没有规定生效时刻。

v1 已规定按所选时段生成当天任务，因此不是完全没有旧规则。问题在于新版本加入日历和 N2 后，沿用旧规则会产生新的效果：[当前 generateEvents][code-generate]会生成演示日各个已选时段的任务；[eventsToday][code-events]会过滤掉已停用计划的未处理任务；[停用处理][code-stop]允许具有档案访问权的账号操作。

**触发场景：**

| 场景 | 当前需求没有给出的决定 |
| --- | --- |
| 18:00 新建从今天开始的早餐+晚餐计划 | 是否追造今天早餐的逾期任务；是否立刻向子女发 N2 |
| 当天已点星后又新增计划 | 星星是否重新计算；新增计划从哪个时段生效 |
| 早餐仍未记录，子女停用该药品计划 | 早餐是否仍在今日分母中；不能在未定义规则下通过停用使一天变成“全完成” |
| 更改剂量或提醒时刻 | 对当前任务、已记录任务、后续任务分别何时生效；旧通知怎样取消 |

**建议口径：**明确有效时刻、任务取消规则和分母依据。可采用“新建默认只生成生效后适用任务，补建过去任务需明确选择；已发生或已到期任务保留记录依据；未来取消任务单独标记”的初版。停用不能把未记录事实追溯改写成已处理。子女编辑/停用权限与不能代声明服药事实的边界，应在同一张权限表中说明。

具体采用哪一种生效策略仍需确认，不应把这里的建议直接视为已批准的需求变更。

### R06 · P1：日历已有明确决议，前文仍称未确定

**证据：**[§2.2][v2-calendar-stale]写着无任务日、补打卡、本次无需服用、明确未服用是否算完成“用户尚未确定”；[§7.4][v2-calendar-rule]、D01 和 A46 已给出确认口径。

**影响：**按首页章节开发的人可能只给“全部已服用”点星；按状态章节开发的人会给“全部有明确记录”点星，两端统计可能不同。

**应直接统一的内容：**有任务且当日全部明确处理才点星；“未服用”和“本次无需服用”计为已处理；无任务日不点星；当天补记可计入，跨日补记不回溯改变历史星星；身体数据不纳入分母。这些已有决议无需再作为开放问题询问用户。

同时修订 §6.3、§6.5 中关于 D04 的旧交叉引用：实际量不同或时间不详仍需规定事实状态，但不能因此重新把“是否准确按量服用”混成日历全部记录的条件。月历说明也应清楚写“完成当日用药记录”，避免将星星理解为每次都已服药。

### R07 · P1：去除付费限制的章节包含尚无完整规格的新能力

**证据：**[§10.2–10.3][v2-flat-features]出现“拍照/扫码识药”“复杂方案语音解析”“健康报告导出”，并把报告导出列为基础功能。现有运行文件未发现扫码或导出入口；§5 定义的是手动、图片和语音三种录入，A01–A47 中也没有独立验证扫码和报告导出的通过条件。

**影响：**开发者会对“全部开放”产生不同解释：仅移除权限门槛，还是本次还要新建扫码、批量医嘱录入和导出系统。它们都可能明显增加工作量，不能靠一句开放原则完成规格定义。

**建议分别定稿：**

| 能力 | 最少需要补充的定义 |
| --- | --- |
| 扫码识药 | 扫条码、二维码还是拍照识别；识别来源；本次模拟什么；失败如何手动继续 |
| 整段医嘱解析 | 一药多时段还是多药批量；一药早中晚应生成“一条计划、三个时段任务”还是三条计划；逐药核对及不支持分时剂量时的回退 |
| 健康报告导出 | 导出格式、档案与日期范围、包含哪些记录、原始记录还是摘要、操作入口、隐私及演示标识 |

这些需求已经出现在正文，不能在实现时静默删掉。应逐项标明“本次原型演示 / 后续真实服务 / 本次不交付”的明确决策，再配对应验收。§5.2 已规定不支持的复杂剂量不可错误合并，这条限制应被整段解析明确引用。

## 2. 另外三组最好在本次澄清的细节

### R08 · P2：延后操作和家属提醒的可用条件

**证据：**[§6.4][v2-snooze]先询问“多久以后，或几点再提醒”，后面又限定只能 5 或 30 分钟；[N3][v2-notifications]面向未记录任务，同时又提及已有“未服用”记录的通知详情。[D10][v2-d10]仍保留频控等未决事项。

建议把问题拆成可执行的小规则：

| 情况 | 需要的口径 |
| --- | --- |
| 语音说 10 分钟后、晚上九点 | 当前仅支持 5/30 分钟时明确告知，并请用户选择，不能静默四舍五入 |
| 尚未到提醒点，或任务早已逾期，且尚未用延后 | 是否允许延后；已逾期后延后是否暂时隐藏红点；这是现有“一次延后”决议没有完全覆盖的资格问题 |
| 同名药物、同药多计划、次日相同时段 | 延后机会建议按唯一当次任务计数，包含计划、档案、业务日期和时段；不按药名永久累计 |
| 延后保护期内子女点击 N3 | 拒绝、提示正在延后，还是允许核对提醒；必须避免无意绕过长辈刚选择的延后 |
| 已记录为未服用后子女点击 N3 | 是否允许继续询问本人；已服用/无需服用/取消任务的入口怎样处理 |
| 连点或多名子女同时提醒 | 原型也需要确定的去重/冷却反馈；真实通知延迟指标可以在平台阶段细化 |

真实 APP 还需处理“长辈离线设置延后、服务端尚未收到”的情况。§12.3 已要求显示同步状态；应进一步说明本地延后何时获得服务端确认、N2 抑制以什么状态为准。不能一面承认离线未同步，一面无条件承诺子女端已经同步停止 N2。

### R09 · P2：陪伴形象一次点击有两个动作，“换装”没有独立定义

**证据：**[§10.1][v2-mascot]连续规定“点击形象”打开形象选择与换装卡，又规定“轻触形象”打开管家锦囊。这是同一种手势的两个目标。

**建议：**点击形象打开选择/外观面板，点击气泡打开相应引导，分别设置可访问名称。“换形象”与“给当前形象换衣服”也应明确是否为同一功能；如果真的做换装，需要选项、素材、保存字段和验收，当前数据只列出 mascot 形象标识。

两端都展示形象，但全局助手的明确入口在长辈首页。子女端气泡应按角色提供加计划、记录身体数据、查看记录或提醒等入口；不能承诺点击后直接替长辈打卡。§12.2 的权限约束已存在，这里需要补的是符合该约束的落地交互。

### R10 · P2：跨午夜延后、日历日界和演示时钟需要联合说明

**证据：**§6.4 允许延后跨午夜且保留原任务；§7.4 确认跨日补记不改变旧日星星；[§5.3][v2-slot-boundary]又写“00:00～05:00 暂不生成任务，若有计划跨入该区间按最早时段归类”，D02 没有解释“最早时段”是指什么。

需要区分四种东西：新建 02:00 的固定计划、前一天睡前任务的延后提醒、前一天未记录任务、05:00 的新早餐任务。延后到凌晨的旧任务不能因为“最早时段归类”而变成早餐任务。

23:50 延后 30 分钟、次日 00:10 完成记录，按当前已确认的跨日口径，原日星星不补亮。**这本身不是逻辑矛盾，而是既定规则与跨夜延后组合后的结果。**应说明该结果，并明确日界所用时区、离线当日记录次日同步、跨日撤销/更正怎样影响完成判定。

当前原型固定演示日且演示时刻为 HH:mm。后续验收应保留固定基准日，通过受控日期偏移或专门跨日场景验证午夜行为，不能把 23:50→00:20 错算为同一天时间倒退，也不必为测试改成系统当天。

## 3. 已列为待定，但部分不能等到真实上线前再选

[§15.2][v2-decisions]已主动列出这些问题；下表不是新增发现，而是实施优先级建议。建议为每项增加“影响哪一阶段、原型暂用哪种明确规则、谁确认”的列。

| 待定项 | 本次原型开始相关功能前至少要确定什么 |
| --- | --- |
| D03 提醒时间 | 是否限定在所属时段；建议限定且分钟步长为 1，避免提醒出现在逾期之后 |
| D04 实际量、部分服用、时间不详 | 记录状态、快捷入口和更正方式；日历计的是明确记录，不重新混成服药达标 |
| D05 无计划的新药记录 | 本次采用已有计划匹配/明确创建后关联，还是新建临时记录模型；不要让演示分支假装已经完整支持 |
| D07 历史与计划生效 | 哪些历史可补记或更正；新建/编辑/停用生效时点及通知、分母影响 |
| D08 BMI | 本次是否引用旧身高；采用哪条、如何标注来源、同日多条记录如何排序 |
| D13 记录对象 | 带入当前长辈还是强制选择；切换对象后保留哪些草稿，确认页必须一致 |
| D14 看板入口 | 模块顺序、子女加药入口；历史月份可以继续留作后续决策 |
| D15 形象 | 一次点击行为、换形象与换装的范围；具体素材可随视觉评审确定 |

## 4. 建议补到验收清单的边界场景
